# Plan: Zusätzliche Drucker für einzelne Produkte

> Source PRD: `docs/prds/prd-stationsmodell.md` (Variante Z, von Nico freigegeben)

## Goal

Die Seite „Bondrucker" bleibt für jeden Verein, wie sie ist. Darunter kann der Admin optional benannte Zusatzdrucker anlegen (Name, Drucker-IP, Bonmodus), ihnen einzelne Produkte zuordnen und je Zusatzdrucker einen Testbon senden. Ein zugeordnetes Produkt druckt seinen Arbeitsbon am Zusatzdrucker, jedes andere wie heute an der Druckstation seiner Kategorie. Ohne Zusatzdrucker ändert sich am Druckpfad nichts.

## Architectural decisions

- **Schema:** eine additive Migration `database/migrations/NN_zusatzdrucker.up.sql`, `NN` = nächste freie ab 17 (Reihenfolge der Feature-Spur: #145, Auto-Pfand, Zusatzdrucker; der Lead setzt die endgültige Nummer beim Landen). In `BEGIN; … COMMIT;`, mit `COMMENT ON` je Tabelle und Spalte wie in `01_initial.up.sql`:
  - `zusatzdrucker`: `id INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`, `name TEXT NOT NULL`, `drucker_ip TEXT NOT NULL` (leer = kein Drucker), `bonmodus TEXT NOT NULL CHECK (bonmodus IN ('pro_position', 'pro_bestellung'))`, `updated_at TIMESTAMPTZ NOT NULL` (wie `druckstationen`, kein `created_at`).
  - `zusatzdrucker_produkte`: `produkt_id INT PRIMARY KEY REFERENCES produkte(id) ON DELETE CASCADE`, `zusatzdrucker_id INT NOT NULL REFERENCES zusatzdrucker(id) ON DELETE CASCADE`, Index auf `zusatzdrucker_id`. Der Primärschlüssel erzwingt „höchstens ein Zusatzdrucker je Produkt". Produkte werden in Produktion nie hart gelöscht; die Kaskade auf `produkt_id` hält nur Test-Teardowns und den Seed-Reset frei.
  - `druckstationen` bleibt unberührt, keine Datenübernahme, beide Tabellen starten leer.
- **Kein Event, kein Event-Typ, kein Kassenjournal-Eingriff.** Zusatzdrucker sind Konfiguration wie `druckstationen`: CRUD mit hartem Löschen (PRD: nichts verweist auf sie, ein Soft Delete hätte keine Historie zu bewahren).
- **Modul:** Alles lebt im Druck-Modul. Domäne `backend/domain/druckstation/zusatzdrucker.go`, Repository-Methoden auf `druckstation_repo.Repository` in `backend/repository/druckstation_repo/zusatzdrucker.go`, Queries in `backend/sqlc/queries/zusatzdrucker.sql`, Application und HTTP im neuen Paket `backend/api/druck/zusatzdrucker/`. Produkt-Aggregat, Produktdialog und Produkt-Endpunkte bleiben unverändert.
- **Auflösungsregel an genau einer Stelle:** `backend/api/druck/bondruck/application/arbeitsbon_policy.go` bekommt je Variante den Zusatzdrucker ihres Produkts (`map[int]druckstation.Zusatzdrucker`, Schlüssel `VarianteID`). Zusatzdrucker des Produkts vor Druckstation der Kategorie; ein zugeordneter Zusatzdrucker ohne IP druckt nichts und fällt **nicht** auf die Kategorie zurück. Direktverkauf: erst „Kein Bon", dann Abholbon für alle Positionen, sonst die aufgelöste Gruppierung. Die Gruppen entstehen in der Reihenfolge ihres ersten Auftretens in der Bestellung, damit die Auftragsliste deterministisch ist.
- **Laden der Zuordnung:** Die Aufrufer laden sie mit einer Abfrage über die Varianten-IDs der angereicherten Positionen (`produkt_varianten` → `zusatzdrucker_produkte` → `zusatzdrucker`). Die Methode hängt an derselben `druckstationRepo`-Schnittstelle wie `GetKonfigurierteDruckstationen()`, damit `backend/api/deps.go` unverändert bleibt.
- **API (alle POST, Admin-Rolle, englische Verben für Konfiguration nach D12):**

  | Endpunkt                               | Body                              | Antwort                                                                                                                                         |
  | -------------------------------------- | --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
  | `/admin/get-zusatzdrucker`             | `{}`                              | `{ zusatzdrucker: [{ id, name, druckerIp, bonmodus, produkte: [{ id, name }] }], produktAuswahl: [{ id, name, kategorie, zusatzdruckerName }] }` |
  | `/admin/create-zusatzdrucker`          | `{ name }`                        | `{ id }`; startet mit leerer IP und `pro_position`                                                                                              |
  | `/admin/update-zusatzdrucker`          | `{ id, name, druckerIp, bonmodus }` | leer                                                                                                                                          |
  | `/admin/delete-zusatzdrucker`          | `{ id }`                          | leer; entfernt die Zuordnungen in derselben Transaktion (Kaskade)                                                                               |
  | `/admin/zusatzdrucker-testbon-drucken` | `{ id }`                          | leer; Referenz `testdruck:<Name>`                                                                                                               |
  | `/admin/assign-produkt-zusatzdrucker`  | `{ produktId, zusatzdruckerId }`  | leer; eine bestehende Zuordnung wandert                                                                                                        |
  | `/admin/unassign-produkt-zusatzdrucker` | `{ produktId }`                  | leer                                                                                                                                            |

  `produkte` und `produktAuswahl` enthalten nur nicht gelöschte Produkte, sortiert wie die Produktverwaltung (`kategorie, reihenfolge, id`). `zusatzdruckerName` ist leer ohne Zuordnung. Phase 1 liefert `get-zusatzdrucker` noch ohne `produkte` und `produktAuswahl`.
- **Fehlercodes:** `zusatzdrucker_not_found` (Ändern, Löschen oder Testbon eines unbekannten Zusatzdruckers), `zusatzdrucker_nicht_konfiguriert` (Testbon ohne IP), `zuordnung_nicht_moeglich` (Produkt gelöscht oder Zusatzdrucker fehlt; das eine `INSERT … SELECT` unterscheidet beides nicht), `validation_error` (ungültige Domäne). Entfernen einer nicht bestehenden Zuordnung ist ein Erfolg. Jeder neue Sentinel steht im Handler, sonst schlägt `TestErrorMappingContract` an.
- **Validierung:** zog im Handler, Zod im Frontend. Neue Domänen-Schemas `druckstation.ZusatzdruckerIDSchema` (1 bis `math.MaxInt32`) und `druckstation.ZusatzdruckerNameSchema` (getrimmt, 3 bis 100 Zeichen wie Produkt- und Tischname); beide bekommen eine Zeile in `backend/api/schema_grenzen_test.go`. Frontend-Name über `createNameSchema(100)` aus `frontend/src/lib/nameSchema.ts`. Bonmodus des Zusatzdruckers: nur `pro_position` und `pro_bestellung`.
- **Testbon:** `escpos.FormatTestbon(name, jetzt)` unverändert, Referenz `testdruck:<Name>`. `formatDruckauftragReferenz()` im Frontend zeigt dafür schon „Testbon <Name>" (gepinnt durch den Fall `testdruck:foo` in `DruckstationBackend.test.ts`); kein Frontend-Code für die Fehlerliste.
- **Seed:** Das Demo-Drehbuch bekommt keinen Zusatzdrucker (D14). `SeedTruncateAll` leert die beiden neuen Tabellen mit, damit jede E2E-Spec aus demselben Zustand startet.
- **Print-Relay, Kassenbeleg, Produktstatistik, DSFinV-K:** unverändert.

Die Phase legt dafür das ganze Schema und alle Repository-Methoden an, auch die der Zuordnung; Phase 2 und 3 schreiben danach keine SQL- oder Repository-Datei mehr und laufen parallel.

### What to build

Eine Tischbestellung oder ein Direktverkauf mit einem zugeordneten Produkt erzeugt dessen Arbeitsbon an der IP des Zusatzdruckers, im Bonmodus des Zusatzdruckers. Alle übrigen Positionen drucken wie heute.

- **Policy:** `CreateArbeitsbonAuftraegeFromEvent(evt, druckstationen, zusatzdrucker map[int]druckstation.Zusatzdrucker, tischName)`. `createStationsAuftraegeFromData()` gruppiert nach Druckziel (Zusatzdrucker-ID, sonst Kategorie) in der Reihenfolge des ersten Auftretens; je Ziel gelten dessen IP und Bonmodus; ein Ziel ohne IP erzeugt keinen Auftrag. `createDirektverkaufAuftraege()` behält „Kein Bon" und Abholbon vor der Auflösung. Referenzen bleiben `bestellung-aufgenommen:<id>` und `direktverkauf-getaetigt:<id>`. Der Doc-Kommentar nennt die Regel einmal.
- **Aufrufer:** `druckstationRepo` in `tischgeschaeft` und `direktverkauf` bekommt `GetZusatzdruckerJeVariante()`. `BestellungAufnehmen()` und `DirektverkaufTaetigen()` laden die Zuordnung nach `enrichment.EnrichPositionen()` über die `VarianteID` der Positionen, ein Fehler ergibt `ErrDatabase` wie beim Laden der Druckstationen, und reichen sie an die Policy.
- **Fakes:** `mockDruckstationRepo` in beiden `command_test.go` bekommt ein Feld für die Zuordnung, `keineDruckstationen` liefert eine leere Map.
- **Seed:** `buildDruckauftraege()` übergibt `nil`; die Demo-Historie bleibt byte-gleich.
- **Doku:**
  - `docs/handbuch.md` §3.12: Der Policy-Eintrag „Arbeitsbon-Druck nach Kategorie (K-12)" verliert „nach Kategorie", die Regel steht in §4.5.
  - `docs/handbuch.md` §4.5: Die Policy gruppiert nach Druckziel; Auflösungsregel „Zusatzdrucker des Produkts vor Druckstation der Kategorie", Zusatzdrucker ohne IP druckt nicht; im Direktverkauf-Routing der dritte Punkt mit Zusatzdrucker.
  - `docs/backlog.md`: Eintrag „Stationsmodell (#146)" entfällt.
  - `docs/decisions.md`: neue Zeile mit der nächsten freien D-Nummer, ohne Dateipfad. Entwurf: „**Zusatzdrucker statt Stationsmodell.** Arbeitsbons drucken an der Druckstation ihrer Kategorie; ein optionaler, benannter Zusatzdrucker übernimmt einzeln zugeordnete Produkte. Die Kategoriestationen bleiben, damit ein Verein ohne Bedarf nichts umstellt. Die Zuordnung hängt am Produkt, nicht an der Variante; eine Variante mit eigenem Ort wird ein eigenes Produkt. Wieder aufgreifen, wenn ein Verein mehr Ausgabeorte meldet, als Zusatzdrucker handhabbar abbilden."
