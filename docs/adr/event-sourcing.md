# ADR: Event-Sourcing für Tisch-Operationen — Bewertung und Entscheidung gegen reines CRUD

## Status

**Entschieden** — Event-Sourcing wird für Tisch-Operationen eingesetzt, CRUD für Stammdaten.

## Kontext

jotti ist ein Kassensystem für Vereinsfeste. Servicekräfte nehmen Bestellungen auf, liefern aus, kassieren und stornieren — alles pro Tisch. Die zentrale Frage ist, wie die Tisch-Operationen (Bestellungen, Zahlungen, Lieferungen, Stornierungen) persistiert werden.

Zwei grundsätzliche Ansätze stehen zur Wahl:

1. **Event-Sourcing**: Jede Aktion wird als unveränderliches Event gespeichert. Der aktuelle Zustand wird durch Replay aller Events rekonstruiert.
2. **CRUD**: Jede Aktion wird in dedizierten relationalen Tabellen gespeichert. Der aktuelle Zustand wird per SQL-Aggregation berechnet.

Stammdaten (Benutzer, Produkte, Tische) werden in beiden Varianten per CRUD verwaltet — das steht nicht zur Debatte. Die Entscheidung betrifft ausschließlich die Tisch-Operationen.

---

## Entscheidung

**Event-Sourcing für Tisch-Operationen, CRUD für Stammdaten** (hybride Architektur).

Tisch-Operationen werden als immutable Events in einer generischen `events`-Tabelle gespeichert. Stammdaten verbleiben in klassischen CRUD-Tabellen.

---

## Bewertete Alternativen

### Alternative A: Event-Sourcing (gewählt)

Alle Tisch-Operationen werden als Events in einer einzigen `events`-Tabelle gespeichert:

```sql
CREATE TABLE events (
    id        INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id   INT REFERENCES users(id) NOT NULL,
    type      TEXT NOT NULL,           -- z.B. "table.order-placed:v1"
    subject   TEXT NOT NULL,           -- z.B. "table:42"
    timestamp TIMESTAMPTZ NOT NULL,
    data      JSONB NOT NULL           -- Event-spezifische Daten
);
```

Append-Only wird durch DB-Trigger erzwungen (kein UPDATE, DELETE, TRUNCATE). Event-Typen sind versioniert (`:v1`-Suffix). Der Zustand wird in Go-Code rekonstruiert. Snapshots (selbst Events vom Typ `table.snapshot:v1`) optimieren die Leseperformance.

**Schreiboperationen**: Ein einzelnes `INSERT INTO events` pro Aktion — alle Daten (Positionen, Preise, Kommentar) sind im `data`-JSONB-Feld enthalten.

**Leseoperationen**: Events laden → in Go iterieren → Zustand berechnen:

- Balance = Σ Bestellungen − Σ Zahlungen − Σ Stornierungen
- Unbezahlte Positionen = bestellt − bezahlt − storniert (via `accumulateVariants`/`reduceVariants`)
- History = alle Events eines Tisches in chronologischer Reihenfolge

### Alternative B: Reines CRUD (verworfen)

Jeder Operationstyp bekommt eigene relationale Tabellen (Header + Items):

```
orders + order_items
payments + payment_items
deliveries + delivery_items
cancelations + cancelation_items
```

Das ergibt **8 Tabellen** statt einer, mit typisierten Spalten, expliziten Fremdschlüsseln und referenzieller Integrität auf DB-Ebene.

**Schreiboperationen**: Transaktion mit 1+N `INSERT`s (Header + N Items pro Aktion).

**Leseoperationen**: SQL-Aggregation, z.B. Balance via `SUM`-Subqueries über 3 Tabellen. Unbezahlte Positionen erfordern verschachtelte Subqueries über mehrere Tabellen mit Joins. History müsste über `UNION ALL` über 4 Tabellen zusammengesetzt werden.

## Begründung

### 1. Audit-Trail ist eine Kernanforderung

In einem Kassensystem muss nachvollziehbar sein, wer wann was bestellt, bezahlt, geliefert oder storniert hat. Event-Sourcing liefert das automatisch durch die Append-Only-Natur des Event Stores. Eine CRUD-Implementierung müsste einen separaten Audit-Mechanismus aufbauen und pflegen, was die vermeintliche Einfachheit relativiert.

### 2. Immutabilität schützt vor Manipulation

In einem System, das Geldbeträge verwaltet, dürfen einmal erfasste Operationen nicht nachträglich verändert werden. Event-Sourcing erzwingt das strukturell (Append-Only-Store mit DB-Triggern). In einem CRUD-System müsste diese Garantie separat implementiert werden.

### 3. Begrenzte Komplexitätskosten

Die Zustandsrekonstruktion betrifft nur Tisch-Operationen, nicht das gesamte System. Stammdaten bleiben CRUD. Die hybride Architektur hält die Event-Sourcing-Komplexität auf einen überschaubaren Bereich begrenzt.

### 4. Snapshots adressieren das Performance-Problem

Die lineare Lese-Komplexität wird durch den Snapshot-Mechanismus effektiv abgemildert. In der Praxis werden Tische regelmäßig abgerechnet — die Event-Kette pro Tisch bleibt kurz.

### 5. Schema-Flexibilität

Zukünftige Features (Umbuchungen, Rabatte, Trinkgeld) erfordern nur neue Event-Typen, keine Schema-Migrationen. Das reduziert das Risiko von Datenmigrations-Fehlern im Produktivbetrieb.

---

## Akzeptierte Nachteile

- **Keine referenzielle Integrität auf DB-Ebene** für Tisch-Operationen. Validierung liegt in der Anwendung (zog-Schemas auf Event-Data und Domain-Modellen).
- **JSONB-Daten nicht typsicher auf DB-Ebene.** Fehlerhafte Daten können nur durch Anwendungsvalidierung verhindert werden.
- **Doppelte Validierung** nötig (Event-Data + Domain-Modell), da die Datenbank keine Struktur erzwingt.
- **Höhere Einstiegshürde** für neue Entwickler (Zustandsrekonstruktion, Snapshots, Event-Versionierung).
- **Erschwertes Ad-hoc-Querying.** Analysen wie „Umsatz pro Produkt heute" erfordern JSONB-Parsing in SQL statt einfacher `GROUP BY`-Abfragen.

## Implementierungsdetails

### Event-Modell

Events orientieren sich am [CloudEvents](https://cloudevents.io/)-Standard:

```go
type Event struct {
    ID      int              `json:"id"`
    UserID  int              `json:"userId"`
    Type    string           `json:"type"`      // z.B. "table.order-placed:v1"
    Time    time.Time        `json:"time"`
    Subject string           `json:"subject"`   // z.B. "table:42"
    Data    json.RawMessage  `json:"data"`
}
```

### Event-Typen

| Event-Typ                     | Beschreibung          |
| ----------------------------- | --------------------- |
| `table.order-placed:v1`       | Bestellung aufgegeben |
| `table.payment-registered:v1` | Zahlung registriert   |
| `table.variants-canceled:v1`  | Positionen storniert  |
| `table.variants-delivered:v1` | Positionen geliefert  |
| `table.snapshot:v1`           | Zustandssnapshot      |

### Append-Only-Garantie

Auf Datenbankebene durch mehrere Mechanismen erzwungen:

1. **Privilege Revocation**: Nur SELECT und INSERT erlaubt.
2. **Trigger gegen UPDATE/DELETE/TRUNCATE**: Lösen Exceptions aus.

### Snapshot-Mechanismus

Snapshots sind selbst Events vom Typ `table.snapshot:v1` und enthalten den berechneten Zustand (Balance, unbezahlte/ungelieferte Positionen, Gesamtzahlungen). Die optimierte Leseabfrage `ReadEventsWithSnapshot()` lädt den letzten Snapshot + nachfolgende Events in einer einzigen SQL-Abfrage.

### CQRS-Trennung

Die Application-Schicht trennt Schreib- und Leseoperationen:

- **Commands** erstellen Events: `PlaceTableOrder`, `RegisterTablePayment`, `CancelTableVariants`, `DeliverTableVariants`, `CreateTableSnapshot`
- **Queries** rekonstruieren Zustand: `GetTableBalance`, `GetTableHistory`, `GetTableUnpaidVariants`, `GetTableUndeliveredVariants`, `GetTableTotalPayments`
