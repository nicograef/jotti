# Event-Sourcing vs. CRUD in jotti

Dieses Dokument beschreibt im Detail, wie Event-Sourcing in jotti implementiert ist und wie es sich vom klassischen CRUD-Ansatz unterscheidet, der für Stammdaten (Benutzer, Produkte, Tische) verwendet wird.

> **Hintergrund**: Für eine allgemeine Einführung in Event-Sourcing siehe die Artikel [Was ist Event-Sourcing?](https://nicograef.com/articles/was-ist-event-sourcing) und [Event-Sourcing am Beispiel Warenkorb erklärt](https://nicograef.com/articles/event-sourcing-am-beispiel-warenkorb-erklaert).

## Hybride Architektur

jotti verwendet eine **hybride Architektur**: Stammdaten werden mit klassischem CRUD verwaltet, während Tisch-Operationen (Bestellungen, Zahlungen, Lieferungen, Stornierungen) per Event-Sourcing abgebildet werden.

| Bereich             | Persistenz-Muster | Tabellen                       |
| ------------------- | ------------------ | ------------------------------ |
| Benutzer            | CRUD               | `users`                        |
| Produkte & Varianten| CRUD               | `products`, `product_variants` |
| Tisch-Stammdaten    | CRUD               | `tables`                       |
| Tisch-Operationen   | Event-Sourcing     | `events`                       |

**Warum hybrid?** Stammdaten ändern sich selten und haben keinen komplexen Lebenszyklus — CRUD ist hier die einfachste und richtige Lösung. Tisch-Operationen dagegen bilden einen komplexen Workflow ab (bestellen → liefern → bezahlen / stornieren), bei dem jede einzelne Aktion nachvollziehbar bleiben muss. Hier bietet Event-Sourcing klare Vorteile:

- **Lückenloser Audit-Trail**: Wer hat wann was bestellt, geliefert, bezahlt, storniert?
- **Keine verlorene Information**: Auch stornierte oder überbezahlte Posten bleiben im Event-Log erhalten.
- **Zustandsrekonstruktion**: Der aktuelle Kontostand, die offenen Posten und die ungelieferten Produkte eines Tisches können jederzeit aus den Events berechnet werden.

## CRUD-Seite: Stammdaten

### Datenbank-Schema

Stammdaten-Tabellen folgen dem klassischen relationalen Modell mit Auto-Increment-IDs und Soft-Deletes (`status = 'deleted'`):

```sql
-- Beispiel: Benutzer (vereinfacht)
CREATE TABLE users (
    id     INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name   TEXT NOT NULL,
    role   UserRole NOT NULL,
    status EntityStatus NOT NULL,  -- active | inactive | deleted
    ...
);

-- Beispiel: Tisch-Stammdaten (vereinfacht)
CREATE TABLE tables (
    id     INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name   TEXT UNIQUE NOT NULL,
    status EntityStatus NOT NULL,  -- active | inactive | deleted
    ...
);
```

### Repository-Pattern

CRUD-Repositories (`user_repo`, `product_repo`, `table_repo`) implementieren Standard-Operationen:

```
GetAll()     → SELECT ... WHERE status != 'deleted'
GetByID(id)  → SELECT ... WHERE id = $1
Create(obj)  → INSERT INTO ... RETURNING id
Update(obj)  → UPDATE ... SET ... WHERE id = $1
```

Beispiel aus `table_repo`:

```go
func (r Repository) GetTable(ctx context.Context, id int) (table.Table, error) {
    row := r.DB.QueryRowContext(ctx,
        `SELECT id, name, status, created_at FROM tables
         WHERE id = $1 AND status != 'deleted'`, id)
    // ... scan und Konvertierung zum Domain-Modell
}
```

**Wichtig**: Tisch-Stammdaten (Name, Status) werden per CRUD verwaltet. Die **Operationen an einem Tisch** (Bestellungen, Zahlungen, ...) werden separat per Event-Sourcing erfasst. Ein Tisch hat also zwei Aspekte:

1. **Aggregate Root (CRUD)**: Metadaten wie Name und Aktivierungsstatus.
2. **Event Stream (Event-Sourcing)**: Kompletter Verlauf aller Bestellungen, Zahlungen, Lieferungen und Stornierungen.

## Event-Sourcing-Seite: Tisch-Operationen

### Das Event-Modell

Events in jotti orientieren sich am [CloudEvents](https://cloudevents.io/)-Standard der CNCF:

```go
// backend/domain/event/event.go
type Event struct {
    ID      int              `json:"id"`
    UserID  int              `json:"userId"`   // Wer hat die Aktion ausgelöst?
    Type    string           `json:"type"`     // z.B. "table.order-placed:v1"
    Time    time.Time        `json:"time"`     // UTC-Zeitstempel
    Subject string           `json:"subject"`  // z.B. "table:42"
    Data    json.RawMessage  `json:"data"`     // Event-spezifische JSONB-Daten
}
```

Jedes Event wird bei der Erstellung validiert (UserID > 0, Type mindestens 5 Zeichen, Subject mindestens 3 Zeichen, Data nicht leer). Die Factory-Funktion `event.New()` setzt automatisch `Time = time.Now().UTC()`.

### Event-Typen

Alle Event-Typen sind versioniert (`:v1`-Suffix), um zukünftige Schema-Evolution zu ermöglichen:

```go
// backend/domain/table/events.go
EventTypeOrderPlacedV1       = "table.order-placed:v1"
EventTypePaymentRegisteredV1 = "table.payment-registered:v1"
EventTypeVariantsCanceledV1  = "table.variants-canceled:v1"
EventTypeVariantsDeliveredV1 = "table.variants-delivered:v1"
EventTypeSnapshotV1          = "table.snapshot:v1"
```

Das **Subject-Format** ist `"table:<id>"` (z.B. `"table:42"`). Darüber werden alle Events einem Tisch zugeordnet.

### Event-Datenstrukturen

Jeder Event-Typ hat eine eigene Datenstruktur mit zugehörigem `zog`-Validierungsschema:

#### OrderPlaced (Bestellung aufgegeben)

```go
type orderPlacedV1Data struct {
    OrderID         string     `json:"orderId"`         // UUID
    Variants        []LineItem `json:"variants"`         // Bestellte Positionen
    TotalPriceCents int        `json:"totalPriceCents"`  // Gesamtpreis in Cent
    Comment         string     `json:"comment"`          // Optionaler Kommentar (max 100 Zeichen)
}
```

#### PaymentRegistered (Zahlung registriert)

```go
type paymentRegisteredV1Data struct {
    PaymentID         string     `json:"paymentId"`         // UUID
    Variants          []LineItem `json:"variants"`           // Bezahlte Positionen
    TotalPaymentCents int        `json:"totalPaymentCents"`  // Zahlungsbetrag in Cent
    Comment           string     `json:"comment"`
}
```

#### VariantsCanceled (Stornierung)

```go
type variantsCanceledV1Data struct {
    CancelationID         string     `json:"cancelationId"`         // UUID
    Variants              []LineItem `json:"variants"`               // Stornierte Positionen
    TotalCancelationCents int        `json:"totalCancelationCents"`  // Stornierter Betrag in Cent
    Comment               string     `json:"comment"`
}
```

#### VariantsDelivered (Lieferung)

```go
type variantsDeliveredV1Data struct {
    DeliveryID string     `json:"deliveryId"`  // UUID
    Variants   []LineItem `json:"variants"`     // Gelieferte Positionen
    Comment    string     `json:"comment"`
}
```

#### LineItem (Position)

Alle Event-Typen verwenden dieselbe `LineItem`-Struktur für einzelne Positionen:

```go
type LineItem struct {
    ID         int    `json:"id"`          // Produkt-Varianten-ID
    Name       string `json:"name"`        // Anzeigename
    PriceCents int    `json:"priceCents"`  // Preis in Cent
    Quantity   int    `json:"quantity"`    // Menge (≥ 1)
}
```

### Event-Erstellung

Für jeden Event-Typ gibt es eine Factory-Funktion, die:
1. Berechnungen durchführt (z.B. Gesamtpreis aus Varianten)
2. Eine UUID generiert
3. Die Daten gegen das `zog`-Schema validiert
4. Das Event über `event.New()` erstellt

Beispiel für eine Bestellung:

```go
func NewOrderPlacedEvent(userID, tableID int, variants []LineItem, comment string) (e.Event, error) {
    totalPriceCents := 0
    for _, variant := range variants {
        totalPriceCents += variant.PriceCents * variant.Quantity
    }
    data := orderPlacedV1Data{
        OrderID:         uuid.New().String(),
        Variants:        variants,
        TotalPriceCents: totalPriceCents,
        Comment:         comment,
    }
    // Validierung + Event erstellen
    return e.New(userID, string(EventTypeOrderPlacedV1), "table:"+strconv.Itoa(tableID), data)
}
```

### Domain-Modelle aus Events rekonstruieren

Jeder Event-Typ hat auch eine `build*FromEvent()`-Funktion, die ein Event zurück in ein Domain-Modell umwandelt:

```go
func buildOrderFromEvent(event e.Event) (Order, error) {
    // 1. Event-Typ prüfen
    // 2. Table-ID aus Subject parsen ("table:42" → 42)
    // 3. Event-Data deserialisieren und validieren
    // 4. Domain-Modell (Order) zusammenbauen und validieren
    return Order{
        ID: data.OrderID, UserID: event.UserID, TableID: tableID,
        Variants: data.Variants, TotalPriceCents: data.TotalPriceCents,
        Comment: data.Comment, PlacedAt: event.Time,
    }, nil
}
```

## Die Events-Tabelle (Event Store)

### Schema

```sql
CREATE TABLE events (
    id        INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id   INT REFERENCES users(id) NOT NULL,
    type      TEXT NOT NULL,
    subject   TEXT NOT NULL,
    timestamp TIMESTAMPTZ NOT NULL,
    data      JSONB NOT NULL
);
```

### Indizes

```sql
CREATE INDEX idx_events_user_id      ON events(user_id);
CREATE INDEX idx_events_subject      ON events(subject);
CREATE INDEX idx_events_type         ON events(type);
CREATE INDEX idx_events_subject_type ON events(subject, type);
```

Der kombinierte Index `(subject, type)` ist besonders wichtig für die Snapshot-Optimierung, bei der gleichzeitig nach Subject und Typ gefiltert wird.

### Append-Only-Garantie

Die Immutabilität der Events wird auf Datenbankebene durch mehrere Mechanismen erzwungen:

1. **Privilege Revocation**: `REVOKE ALL ON TABLE events FROM PUBLIC; GRANT SELECT, INSERT ON TABLE events TO PUBLIC;`
2. **Trigger gegen UPDATE**: Löst eine Exception aus, wenn ein Event aktualisiert werden soll.
3. **Trigger gegen DELETE**: Löst eine Exception aus, wenn ein Event gelöscht werden soll.
4. **Trigger gegen TRUNCATE**: Verhindert das Leeren der gesamten Tabelle.

```sql
CREATE OR REPLACE FUNCTION prevent_event_mutation() RETURNS TRIGGER AS $$
BEGIN
    RAISE EXCEPTION 'events table is append-only: % not allowed', TG_OP;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER events_no_update  BEFORE UPDATE   ON events FOR EACH ROW       EXECUTE FUNCTION prevent_event_mutation();
CREATE TRIGGER events_no_delete  BEFORE DELETE   ON events FOR EACH ROW       EXECUTE FUNCTION prevent_event_mutation();
CREATE TRIGGER events_no_truncate BEFORE TRUNCATE ON events FOR EACH STATEMENT EXECUTE FUNCTION prevent_event_mutation();
```

Diese Trigger schützen auch vor dem Table-Owner, der PostgreSQL-Privilege-Checks normalerweise umgeht.

## Event Repository

Das `event_repo` (`backend/repository/event_repo/repo.go`) ist die einzige Zugriffsschicht auf die `events`-Tabelle:

### Schreiben

```go
func (r Repository) WriteEvent(ctx context.Context, e event.Event) (int, error) {
    var id int
    err := r.DB.QueryRowContext(ctx,
        `INSERT INTO events (user_id, type, subject, data, timestamp)
         VALUES ($1, $2, $3, $4, $5) RETURNING id`,
        e.UserID, e.Type, e.Subject, e.Data, e.Time,
    ).Scan(&id)
    return id, err
}
```

Es gibt nur `INSERT` — kein `UPDATE`, kein `DELETE`.

### Lesen

Es gibt mehrere Lese-Methoden für unterschiedliche Anwendungsfälle:

| Methode                    | Anwendungsfall                                                         |
| -------------------------- | ---------------------------------------------------------------------- |
| `ReadEvent(id)`            | Einzelnes Event lesen                                                  |
| `ReadEventsBySubject(subj)`| Alle Events eines Tisches lesen (für vollständige History)             |
| `ReadEventsSinceID(subj, fromID)` | Events ab einer bestimmten ID lesen                             |
| `GetLastSnapshotID(subj, type)` | ID des letzten Snapshots ermitteln                                |
| `ReadEventsWithSnapshot(subj, type)` | Snapshot + nachfolgende Events lesen (optimierte Abfrage)    |

### Die optimierte Snapshot-Abfrage

Die Methode `ReadEventsWithSnapshot()` kombiniert Snapshot-Suche und Event-Lesen in einer einzigen SQL-Abfrage:

```sql
WITH last_snapshot AS (
    SELECT COALESCE(MAX(id), 0) AS id
    FROM events
    WHERE subject = $1 AND type = $2
)
SELECT e.id, e.user_id, e.type, e.subject, e.data, e.timestamp
FROM events e, last_snapshot ls
WHERE e.subject = $1 AND e.id >= ls.id
ORDER BY e.id ASC
```

**Ablauf**: Zuerst wird die ID des letzten Snapshots ermittelt. Falls kein Snapshot existiert (`COALESCE → 0`), werden alle Events des Subjects geladen. Andernfalls werden der Snapshot und alle nachfolgenden Events geladen.

## Zustandsrekonstruktion aus Events

Die Kernlogik der Zustandsrekonstruktion befindet sich in `backend/domain/table/events.go`. Der aktuelle Zustand eines Tisches wird berechnet, indem alle Events der Reihe nach durchlaufen und angewendet werden.

### Balance (Kontostand)

```
Balance = Σ Bestellungen − Σ Zahlungen − Σ Stornierungen
```

```go
func GetBalanceFromEvents(events []e.Event) (int, error) {
    balanceCents := 0
    for _, event := range events {
        switch event.Type {
        case "table.snapshot:v1":
            snapshot, _ := buildSnapshotFromEvent(event)
            balanceCents = snapshot.BalanceCents          // Snapshot als Ausgangspunkt
        case "table.order-placed:v1":
            order, _ := buildOrderFromEvent(event)
            balanceCents += order.TotalPriceCents         // + Bestellungen
        case "table.payment-registered:v1":
            payment, _ := buildPaymentFromEvent(event)
            balanceCents -= payment.TotalPaymentCents     // − Zahlungen
        case "table.variants-canceled:v1":
            cancelation, _ := buildCancelationFromEvent(event)
            balanceCents -= cancelation.TotalCancelationCents // − Stornierungen
        }
    }
    return balanceCents, nil
}
```

### Unbezahlte Positionen

```
Unbezahlt = bestellt − bezahlt − storniert
```

Events werden mit `accumulateVariants()` (addiert Positionen) und `reduceVariants()` (subtrahiert Positionen) verarbeitet. Positionen werden nach Varianten-ID und Preis zusammengeführt.

```go
func GetUnpaidVariantsFromEvents(events []e.Event) ([]LineItem, error) {
    unpaidVariants := []LineItem{}
    for _, event := range events {
        switch event.Type {
        case "table.snapshot:v1":        unpaidVariants = snapshot.UnpaidVariants
        case "table.order-placed:v1":    unpaidVariants = accumulateVariants(unpaidVariants, order.Variants)
        case "table.payment-registered:v1": unpaidVariants = reduceVariants(unpaidVariants, payment.Variants)
        case "table.variants-canceled:v1":  unpaidVariants = reduceVariants(unpaidVariants, cancelation.Variants)
        }
    }
    return unpaidVariants, nil
}
```

### Ungelieferte Positionen

```
Ungeliefert = bestellt − geliefert − storniert
```

Gleiche Logik wie unbezahlt, aber mit Lieferungen statt Zahlungen.

### Verlauf (History)

`GetHistoryFromEvents()` wandelt alle Events (außer Snapshots) in Domain-Modelle um und gibt sie in umgekehrter Reihenfolge zurück (neuestes Event zuerst).

### Gesamtzahlungen

`GetTotalPaymentsFromEvents()` summiert alle Zahlungsereignisse. Snapshots setzen den Ausgangswert.

## Snapshots

Snapshots sind ein Performance-Optimierungsmechanismus. Ein Snapshot ist selbst ein Event vom Typ `table.snapshot:v1` und enthält den berechneten Zustand eines Tisches zu einem bestimmten Zeitpunkt:

```go
type Snapshot struct {
    TableID             int
    BalanceCents        int        // Aktueller Kontostand
    UnpaidVariants      []LineItem // Liste unbezahlter Positionen
    UndeliveredVariants []LineItem // Liste ungelieferter Positionen
    TotalPaymentsCents  int        // Gesamtsumme aller Zahlungen
    CreatedAt           time.Time
}
```

### Snapshot-Erstellung

Snapshots werden über die Application-Service-Methode `CreateTableSnapshot()` erstellt:

1. Alle Events des Tisches lesen (mit vorherigem Snapshot als Ausgangspunkt)
2. Den aktuellen Zustand berechnen (Balance, unbezahlt, ungeliefert, Gesamtzahlungen)
3. Einen neuen Snapshot-Event erstellen und in den Event Store schreiben

Da der Snapshot selbst ein Event ist, wird er im selben Append-Only-Store gespeichert wie alle anderen Events. Das bedeutet:
- Snapshots sind genauso immutabel wie alle anderen Events.
- Die Rekonstruktions-Funktionen erkennen Snapshots und verwenden sie als Ausgangspunkt.
- Beim Lesen mit `ReadEventsWithSnapshot()` wird automatisch der letzte Snapshot + nachfolgende Events geladen.

### Warum Snapshots als Events?

Der Snapshot-as-Event-Ansatz hat Vorteile:
- **Kein separater Speicher nötig**: Snapshots leben im gleichen Event Store.
- **Konsistente Ordnung**: Die Event-ID garantiert die zeitliche Einordnung relativ zu anderen Events.
- **Einfache Abfrage**: `WHERE type = 'table.snapshot:v1' AND subject = 'table:42'` findet alle Snapshots.

## Application Layer: CQRS-Separation

Die Application-Schicht trennt Schreib- und Leseoperationen in separate Structs:

### Commands (Schreiben)

Commands erstellen neue Events und schreiben sie in den Event Store:

| Command                    | Erzeugt Event-Typ                |
| -------------------------- | -------------------------------- |
| `PlaceTableOrder()`        | `table.order-placed:v1`          |
| `RegisterTablePayment()`   | `table.payment-registered:v1`    |
| `CancelTableVariants()`    | `table.variants-canceled:v1`     |
| `DeliverTableVariants()`   | `table.variants-delivered:v1`    |
| `CreateTableSnapshot()`    | `table.snapshot:v1`              |

Jeder Command folgt demselben Muster:

```
1. Domain-Event über Factory-Funktion erstellen (inkl. Validierung)
2. Event über EventRepo.WriteEvent() persistieren
3. Event-ID zurückgeben
```

### Queries (Lesen)

Queries lesen Events und rekonstruieren den Zustand:

| Query                           | Liest Events via                | Berechnet                       |
| ------------------------------- | ------------------------------- | ------------------------------- |
| `GetTableBalance()`             | `ReadEventsWithSnapshot()`      | Balance in Cent                 |
| `GetTableHistory()`             | `ReadEventsBySubject()`         | Chronologischer Verlauf         |
| `GetTableUnpaidVariants()`      | `ReadEventsWithSnapshot()`      | Offene Positionen               |
| `GetTableUndeliveredVariants()` | `ReadEventsWithSnapshot()`      | Noch nicht gelieferte Positionen|
| `GetTableTotalPayments()`       | `ReadEventsWithSnapshot()`      | Gesamtsumme aller Zahlungen     |

**Beachte**: `GetTableHistory()` nutzt `ReadEventsBySubject()` (alle Events), nicht `ReadEventsWithSnapshot()`. Der vollständige Verlauf benötigt alle Events, nicht nur ab dem letzten Snapshot.

## Beispiel: Lebenszyklus einer Bestellung

Ein konkretes Beispiel zeigt, wie die verschiedenen Schichten zusammenspielen:

### 1. Bestellung aufgeben

```
HTTP-Handler empfängt POST /service/place-table-order
    → Application Command: PlaceTableOrder(userID=3, tableID=42, variants=[...], comment="ohne Eis")
        → Domain: NewOrderPlacedEvent(3, 42, variants, "ohne Eis")
            → Berechnet TotalPriceCents, generiert UUID, validiert mit zog
            → Erstellt Event mit Type="table.order-placed:v1", Subject="table:42"
        → Repository: EventRepo.WriteEvent(event)
            → INSERT INTO events (...) VALUES (...) RETURNING id
```

### 2. Lieferung bestätigen

```
HTTP-Handler empfängt POST /service/deliver-table-variants
    → Application Command: DeliverTableVariants(userID=5, tableID=42, variants=[...])
        → Domain: NewVariantsDeliveredEvent(5, 42, variants, "")
        → Repository: EventRepo.WriteEvent(event)
```

### 3. Bezahlung registrieren

```
HTTP-Handler empfängt POST /service/register-table-payment
    → Application Command: RegisterTablePayment(userID=3, tableID=42, variants=[...])
        → Domain: NewPaymentRegisteredEvent(3, 42, variants, "")
        → Repository: EventRepo.WriteEvent(event)
```

### 4. Tisch-Balance abfragen

```
HTTP-Handler empfängt POST /service/get-table-balance
    → Application Query: GetTableBalance(tableID=42)
        → Repository: EventRepo.ReadEventsWithSnapshot("table:42", "table.snapshot:v1")
            → SQL: WITH last_snapshot AS (...) SELECT ... WHERE subject='table:42' AND id >= ls.id
        → Domain: GetBalanceFromEvents(events)
            → Iteriert über Events, berechnet: +Bestellungen −Zahlungen −Stornierungen
        → Gibt Balance in Cent zurück
```

## Vergleich: CRUD vs. Event-Sourcing in jotti

| Aspekt              | CRUD (Stammdaten)                              | Event-Sourcing (Tisch-Operationen)              |
| ------------------- | ---------------------------------------------- | ----------------------------------------------- |
| **Speichert**       | Aktuellen Zustand                              | Alle Änderungen als Events                      |
| **Operationen**     | CREATE, READ, UPDATE, (Soft-)DELETE            | Nur INSERT (append-only) + SELECT               |
| **Abfrage**         | Direkter Tabellen-Zugriff                      | Events lesen → Zustand rekonstruieren           |
| **History**         | Nicht vorhanden                                | Vollständig erhalten                            |
| **Schema**          | Spalten = Felder des Objekts                   | Generische Tabelle (type, subject, data)        |
| **Validierung**     | Auf Domain-Model-Ebene                         | Auf Event-Data UND Domain-Model-Ebene           |
| **Performance**     | O(1) für Einzelzugriff                         | O(n) über alle Events (optimiert durch Snapshots)|
| **Immutabilität**   | Daten werden überschrieben                     | Events sind unveränderlich (DB-Trigger)          |
| **Komplexität**     | Gering                                         | Höher (Rekonstruktion, Snapshots, Versionierung)|

## Zusammenfassung

jotti nutzt Event-Sourcing gezielt dort, wo es einen echten Mehrwert bringt: beim Bestell- und Kassierbetrieb an Tischen. Die Kombination mit CRUD für Stammdaten hält die Gesamtkomplexität beherrschbar.

**Kernprinzipien der Implementierung:**

1. **Append-only Events**: Durch DB-Trigger auf Datenbankebene garantiert — nicht nur auf Applikationsebene.
2. **Versionierte Event-Typen**: `:v1`-Suffix ermöglicht Schema-Evolution ohne Breaking Changes.
3. **Snapshots als Events**: Performance-Optimierung ohne zusätzliche Infrastruktur.
4. **Doppelte Validierung**: Sowohl Event-Daten als auch rekonstruierte Domain-Modelle werden mit `zog`-Schemas validiert.
5. **CQRS-Trennung**: Commands schreiben Events, Queries lesen und rekonstruieren — klar getrennt in der Application-Schicht.
6. **CloudEvents-orientiertes Format**: Standardisiertes Event-Schema mit ID, Type, Time, Subject und Data.
