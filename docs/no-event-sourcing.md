# jotti ohne Event-Sourcing

Dieses Dokument beschreibt, wie jotti implementiert werden würde, wenn **alle Tisch-Operationen** (Bestellungen, Zahlungen, Lieferungen, Stornierungen) statt mit Event-Sourcing mit klassischem CRUD umgesetzt wären. Anschließend werden die Schlüsselunterschiede zur aktuellen Implementierung analysiert und beide Ansätze objektiv verglichen.

> **Kontext**: Die aktuelle jotti-Architektur ist in [Event-Sourcing vs. CRUD](event-sourcing-vs-crud.md) und [Datenbank & Persistenz](database.md) beschrieben.

## Alternative Architektur: Reines CRUD

In einer CRUD-basierten Variante würde jotti **keine generische `events`-Tabelle** verwenden. Stattdessen bekäme jeder Operationstyp eigene, relationale Tabellen mit expliziten Spalten. Der aktuelle Zustand eines Tisches (Balance, offene Posten, ungelieferte Positionen) wäre entweder direkt in einer materialisierten Spalte gespeichert oder würde per SQL-Aggregation aus den einzelnen Tabellen berechnet.

### Datenbank-Schema

Anstelle der generischen `events`-Tabelle würden folgende Tabellen eingeführt:

```sql
-- Bestellungen
CREATE TABLE orders (
    id          INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    uuid        UUID NOT NULL DEFAULT gen_random_uuid(),
    table_id    INT REFERENCES tables(id) NOT NULL,
    user_id     INT REFERENCES users(id) NOT NULL,
    comment     TEXT NOT NULL DEFAULT '',
    total_price_cents INT NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_orders_table_id ON orders(table_id);
CREATE INDEX idx_orders_user_id ON orders(user_id);

-- Bestellpositionen
CREATE TABLE order_items (
    id              INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id        INT REFERENCES orders(id) NOT NULL,
    variant_id      INT REFERENCES product_variants(id) NOT NULL,
    variant_name    TEXT NOT NULL,
    price_cents     INT NOT NULL,
    quantity        INT NOT NULL CHECK (quantity >= 1)
);

CREATE INDEX idx_order_items_order_id ON order_items(order_id);

-- Zahlungen
CREATE TABLE payments (
    id          INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    uuid        UUID NOT NULL DEFAULT gen_random_uuid(),
    table_id    INT REFERENCES tables(id) NOT NULL,
    user_id     INT REFERENCES users(id) NOT NULL,
    comment     TEXT NOT NULL DEFAULT '',
    total_payment_cents INT NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_payments_table_id ON payments(table_id);

-- Zahlungspositionen
CREATE TABLE payment_items (
    id              INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    payment_id      INT REFERENCES payments(id) NOT NULL,
    variant_id      INT REFERENCES product_variants(id) NOT NULL,
    variant_name    TEXT NOT NULL,
    price_cents     INT NOT NULL,
    quantity        INT NOT NULL CHECK (quantity >= 1)
);

CREATE INDEX idx_payment_items_payment_id ON payment_items(payment_id);

-- Lieferungen
CREATE TABLE deliveries (
    id          INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    uuid        UUID NOT NULL DEFAULT gen_random_uuid(),
    table_id    INT REFERENCES tables(id) NOT NULL,
    user_id     INT REFERENCES users(id) NOT NULL,
    comment     TEXT NOT NULL DEFAULT '',
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_deliveries_table_id ON deliveries(table_id);

-- Lieferpositionen
CREATE TABLE delivery_items (
    id              INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    delivery_id     INT REFERENCES deliveries(id) NOT NULL,
    variant_id      INT REFERENCES product_variants(id) NOT NULL,
    variant_name    TEXT NOT NULL,
    price_cents     INT NOT NULL,
    quantity        INT NOT NULL CHECK (quantity >= 1)
);

CREATE INDEX idx_delivery_items_delivery_id ON delivery_items(delivery_id);

-- Stornierungen
CREATE TABLE cancelations (
    id          INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    uuid        UUID NOT NULL DEFAULT gen_random_uuid(),
    table_id    INT REFERENCES tables(id) NOT NULL,
    user_id     INT REFERENCES users(id) NOT NULL,
    comment     TEXT NOT NULL DEFAULT '',
    total_cancelation_cents INT NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_cancelations_table_id ON cancelations(table_id);

-- Stornierungspositionen
CREATE TABLE cancelation_items (
    id              INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    cancelation_id  INT REFERENCES cancelations(id) NOT NULL,
    variant_id      INT REFERENCES product_variants(id) NOT NULL,
    variant_name    TEXT NOT NULL,
    price_cents     INT NOT NULL,
    quantity        INT NOT NULL CHECK (quantity >= 1)
);

CREATE INDEX idx_cancelation_items_cancelation_id ON cancelation_items(cancelation_id);
```

**Wesentliche Unterschiede zum Event-Sourcing-Schema:**

- **8 neue Tabellen** statt einer generischen `events`-Tabelle (4 Header-Tabellen + 4 Items-Tabellen).
- **Explizite Fremdschlüssel** (`table_id`, `user_id`, `variant_id`) statt generischer Felder (`subject`, `data`).
- **Typsichere Spalten** statt JSONB: Preise, Mengen und IDs sind als `INT` definiert — die Datenbank selbst erzwingt Typen.
- **Referenzielle Integrität** über Foreign Keys: Die Datenbank garantiert, dass keine Bestellung auf einen nicht existierenden Tisch verweist.
- **Keine Append-Only-Einschränkung** nötig: Es gibt keine Trigger gegen UPDATE/DELETE, da die Tabellen normale CRUD-Tabellen sind. Ob Updates und Deletes erlaubt sind, wird auf Applikationsebene gesteuert.

### Domain-Modelle

Die Domain-Modelle würden weitgehend identisch bleiben. Die bestehenden Structs `Order`, `Payment`, `Delivery`, `Cancelation` und `LineItem` wären weiterhin gültig. Der Unterschied liegt darin, wie sie persistiert und gelesen werden:

```go
// Identisch zum bestehenden Modell
type Order struct {
    ID              string     `json:"id"`
    UserID          int        `json:"userId"`
    TableID         int        `json:"tableId"`
    Variants        []LineItem `json:"variants"`
    TotalPriceCents int        `json:"totalPriceCents"`
    Comment         string     `json:"comment"`
    PlacedAt        time.Time  `json:"placedAt"`
}
```

**Was wegfallen würde:**
- Die Event-Typen (`EventTypeOrderPlacedV1`, etc.) und die Event-Datenstrukturen (`orderPlacedV1Data`, etc.)
- Die `build*FromEvent()`-Funktionen, die Events zurück in Domain-Modelle umwandeln
- Die Zustandsrekonstruktions-Logik (`GetBalanceFromEvents`, `GetUnpaidVariantsFromEvents`, etc.)
- Die Hilfsfunktionen `accumulateVariants()` und `reduceVariants()`
- Das gesamte Snapshot-Konzept (`Snapshot`, `NewSnapshotEvent`, `buildSnapshotFromEvent`)
- Die `event.Event`-Struktur und das generische Event-Modell

### Repository-Schicht

Anstelle eines generischen `event_repo` gäbe es dedizierte Repositories mit typisierten SQL-Abfragen:

#### Order-Repository

```go
type OrderRepository struct {
    DB *sql.DB
}

func (r *OrderRepository) CreateOrder(ctx context.Context, order Order) (int, error) {
    tx, err := r.DB.BeginTx(ctx, nil)
    if err != nil {
        return 0, err
    }
    defer tx.Rollback()

    var id int
    err = tx.QueryRowContext(ctx,
        `INSERT INTO orders (table_id, user_id, comment, total_price_cents, created_at)
         VALUES ($1, $2, $3, $4, $5) RETURNING id`,
        order.TableID, order.UserID, order.Comment, order.TotalPriceCents, order.PlacedAt,
    ).Scan(&id)
    if err != nil {
        return 0, err
    }

    for _, item := range order.Variants {
        _, err = tx.ExecContext(ctx,
            `INSERT INTO order_items (order_id, variant_id, variant_name, price_cents, quantity)
             VALUES ($1, $2, $3, $4, $5)`,
            id, item.ID, item.Name, item.PriceCents, item.Quantity,
        )
        if err != nil {
            return 0, err
        }
    }

    return id, tx.Commit()
}

func (r *OrderRepository) GetOrdersByTable(ctx context.Context, tableID int) ([]Order, error) {
    // SELECT mit JOIN auf order_items, gruppiert nach Order
    // ...
}
```

**Muster**: Jede Schreiboperation (Bestellung, Zahlung, Lieferung, Stornierung) erfordert eine **Transaktion**, da sowohl der Header-Datensatz als auch die zugehörigen Positionen atomar geschrieben werden müssen. Beim Event-Sourcing genügt ein einzelnes `INSERT INTO events`, da alle Daten im `data`-JSONB-Feld enthalten sind.

#### Vergleich der Repository-Interfaces

| Event-Sourcing (aktuell)                     | CRUD (alternativ)                           |
| -------------------------------------------- | ------------------------------------------- |
| `EventRepo.WriteEvent(event)`                | `OrderRepo.CreateOrder(order)` (mit Tx)     |
| `EventRepo.ReadEventsBySubject("table:42")`  | `OrderRepo.GetOrdersByTable(42)`            |
| `EventRepo.ReadEventsWithSnapshot(...)`      | Entfällt — Zustand per SQL-Aggregation      |
| 1 Repository für alle Event-Typen            | 4 separate Repositories                     |

### Application-Schicht

Die Application-Schicht vereinfacht sich, da die CQRS-Trennung in Commands und Queries nicht mehr zwingend nötig ist:

#### Schreiboperationen (Commands)

```go
func (s *TableService) PlaceOrder(ctx context.Context, userID, tableID int,
    variants []LineItem, comment string) (int, error) {

    totalPriceCents := 0
    for _, v := range variants {
        totalPriceCents += v.PriceCents * v.Quantity
    }

    order := Order{
        UserID:          userID,
        TableID:         tableID,
        Variants:        variants,
        TotalPriceCents: totalPriceCents,
        Comment:         comment,
        PlacedAt:        time.Now().UTC(),
    }

    return s.OrderRepo.CreateOrder(ctx, order)
}
```

**Was wegfallen würde:** Das Erstellen eines generischen Events über Factory-Funktionen (`NewOrderPlacedEvent`). Stattdessen wird direkt ein Domain-Modell gebaut und an das Repository übergeben.

#### Leseoperationen (Queries)

Die Leseoperationen werden grundlegend anders — statt Events zu lesen und Zustand in Go zu rekonstruieren, wird der Zustand per SQL-Aggregation berechnet:

```go
func (s *TableService) GetBalance(ctx context.Context, tableID int) (int, error) {
    var balance int
    err := s.DB.QueryRowContext(ctx, `
        SELECT
            COALESCE((SELECT SUM(total_price_cents) FROM orders WHERE table_id = $1), 0)
          - COALESCE((SELECT SUM(total_payment_cents) FROM payments WHERE table_id = $1), 0)
          - COALESCE((SELECT SUM(total_cancelation_cents) FROM cancelations WHERE table_id = $1), 0)
    `, tableID).Scan(&balance)
    return balance, err
}
```

### Zustandsabfragen

Die Zustandsabfragen wären als reine SQL-Abfragen implementiert, ohne Logik in der Anwendung:

#### Balance

```sql
SELECT
    COALESCE((SELECT SUM(total_price_cents) FROM orders WHERE table_id = $1), 0)
  - COALESCE((SELECT SUM(total_payment_cents) FROM payments WHERE table_id = $1), 0)
  - COALESCE((SELECT SUM(total_cancelation_cents) FROM cancelations WHERE table_id = $1), 0)
AS balance_cents
```

#### Unbezahlte Positionen

```sql
SELECT
    oi.variant_id,
    oi.variant_name,
    oi.price_cents,
    SUM(oi.quantity)
      - COALESCE((
          SELECT SUM(pi.quantity)
          FROM payment_items pi
          JOIN payments p ON pi.payment_id = p.id
          WHERE p.table_id = $1
            AND pi.variant_id = oi.variant_id
            AND pi.price_cents = oi.price_cents
        ), 0)
      - COALESCE((
          SELECT SUM(ci.quantity)
          FROM cancelation_items ci
          JOIN cancelations c ON ci.cancelation_id = c.id
          WHERE c.table_id = $1
            AND ci.variant_id = oi.variant_id
            AND ci.price_cents = oi.price_cents
        ), 0)
      AS remaining_quantity
FROM order_items oi
JOIN orders o ON oi.order_id = o.id
WHERE o.table_id = $1
GROUP BY oi.variant_id, oi.variant_name, oi.price_cents
HAVING SUM(oi.quantity)
      - COALESCE((
          SELECT SUM(pi.quantity)
          FROM payment_items pi
          JOIN payments p ON pi.payment_id = p.id
          WHERE p.table_id = $1
            AND pi.variant_id = oi.variant_id
            AND pi.price_cents = oi.price_cents
        ), 0)
      - COALESCE((
          SELECT SUM(ci.quantity)
          FROM cancelation_items ci
          JOIN cancelations c ON ci.cancelation_id = c.id
          WHERE c.table_id = $1
            AND ci.variant_id = oi.variant_id
            AND ci.price_cents = oi.price_cents
        ), 0)
      > 0
```

#### Ungelieferte Positionen

Die Abfrage für ungelieferte Positionen folgt dem gleichen Muster, aber mit `delivery_items`/`deliveries` statt `payment_items`/`payments`.

**Beobachtung**: Die Aggregationsabfragen für unbezahlte und ungelieferte Positionen sind deutlich komplexer als die Balance-Abfrage, da sie auf Positions-Ebene (pro Variante und Preis) aggregieren müssen. Im Event-Sourcing-Ansatz ist diese Logik in Go-Code ausgedrückt (`accumulateVariants`, `reduceVariants`), was lesbarer und einfacher testbar ist als verschachtelte SQL-Subqueries.

### Verlauf (History)

Der Verlauf eines Tisches müsste aus mehreren Tabellen zusammengesetzt werden:

```sql
SELECT 'order' AS type, uuid, user_id, comment, total_price_cents AS amount_cents, created_at
FROM orders WHERE table_id = $1
UNION ALL
SELECT 'payment', uuid, user_id, comment, total_payment_cents, created_at
FROM payments WHERE table_id = $1
UNION ALL
SELECT 'delivery', uuid, user_id, comment, 0, created_at
FROM deliveries WHERE table_id = $1
UNION ALL
SELECT 'cancelation', uuid, user_id, comment, total_cancelation_cents, created_at
FROM cancelations WHERE table_id = $1
ORDER BY created_at DESC
```

Zusätzlich müssten für jeden History-Eintrag die zugehörigen Positionen geladen werden (entweder per N+1-Query oder per JSON-Aggregation), da die Positionen in separaten Tabellen liegen.

Im Event-Sourcing-Ansatz enthält jedes Event bereits alle Positionen im `data`-JSONB-Feld, sodass ein einziges `SELECT ... WHERE subject = 'table:42' ORDER BY id ASC` den kompletten Verlauf mit allen Details liefert.

## Schlüsselunterschiede zur aktuellen Implementierung

### 1. Datenbank-Schema

| Aspekt                   | Event-Sourcing (aktuell)              | CRUD (alternativ)                        |
| ------------------------ | ------------------------------------- | ---------------------------------------- |
| Tabellen für Operationen | 1 (`events`)                          | 8 (`orders`, `order_items`, `payments`, `payment_items`, `deliveries`, `delivery_items`, `cancelations`, `cancelation_items`) |
| Datenformat              | Generisch (`type`, `subject`, `data` als JSONB) | Typisiert (explizite Spalten pro Tabelle) |
| Fremdschlüssel           | Nur `user_id`                         | `table_id`, `user_id`, `variant_id` (volle referenzielle Integrität) |
| Immutabilität            | DB-Trigger verhindern UPDATE/DELETE   | Keine DB-seitige Einschränkung           |
| Schema-Evolution         | Versionierte Event-Typen (`:v1`-Suffix) | SQL-Migrationen (ALTER TABLE)           |

### 2. Schreiboperationen

| Aspekt                   | Event-Sourcing (aktuell)              | CRUD (alternativ)                        |
| ------------------------ | ------------------------------------- | ---------------------------------------- |
| SQL-Statements pro Aktion| 1 `INSERT` (ein Event-Row)            | 1+N `INSERT`s (Header + N Items) in einer Transaktion |
| Datenmodell              | Event → JSONB-Serialisierung          | Domain-Modell → typisierte Spalten       |
| Transaktionen            | Nicht nötig (Single-Insert)           | Erforderlich (Header + Items)            |
| Validierung              | Event-Data + Domain-Modell (doppelt)  | Domain-Modell (einfach)                  |

### 3. Leseoperationen

| Aspekt                    | Event-Sourcing (aktuell)              | CRUD (alternativ)                        |
| ------------------------- | ------------------------------------- | ---------------------------------------- |
| Balance                   | Events laden → in Go iterieren        | Single SQL-Query (3× `SUM`)              |
| Unbezahlte Positionen     | Events laden → `accumulateVariants`/`reduceVariants` | Komplexe SQL mit Subqueries |
| History                   | `SELECT ... WHERE subject ORDER BY id`| `UNION ALL` über 4 Tabellen + Items      |
| Performance-Optimierung   | Snapshots (als Events gespeichert)    | SQL-Indizes, ggf. materialisierte Views  |
| Zustandsrekonstruktion    | In Go-Code (Application Layer)        | In SQL (Database Layer)                  |

### 4. Code-Architektur

| Aspekt                    | Event-Sourcing (aktuell)              | CRUD (alternativ)                        |
| ------------------------- | ------------------------------------- | ---------------------------------------- |
| Repository-Packages       | 1 (`event_repo`)                      | 4 (`order_repo`, `payment_repo`, `delivery_repo`, `cancelation_repo`) |
| Domain-Code               | Event-Factories + Rekonstruktionsfunktionen | Einfache Modelle + Validierung     |
| Application Layer         | CQRS (separate Command/Query-Structs) | Einheitlicher Service                    |
| Testbarkeit der Logik     | Go-Unit-Tests für Rekonstruktion      | SQL-Integration-Tests oder Views         |
| Snapshot-Mechanismus      | Ja (als Events)                       | Nicht nötig                              |

### 5. Datensicherheit und Audit

| Aspekt                    | Event-Sourcing (aktuell)              | CRUD (alternativ)                        |
| ------------------------- | ------------------------------------- | ---------------------------------------- |
| Audit-Trail               | Vollständig (alle Events sind immutabel) | Abhängig von Implementierung (könnte über separate Audit-Tabellen oder Soft-Deletes realisiert werden) |
| Datenmanipulation         | Durch DB-Trigger verhindert           | Möglich ohne zusätzliche Schutzmaßnahmen |
| Fehleranalyse             | Exakter Zustand zu jedem Zeitpunkt rekonstruierbar | Nur aktueller Zustand verfügbar (ohne zusätzliche Audit-Infrastruktur) |

## Analyse: Vor- und Nachteile

### Event-Sourcing (aktuelle Implementierung)

#### Vorteile

1. **Vollständiger Audit-Trail**: Jede Aktion (Bestellung, Zahlung, Lieferung, Stornierung) ist als immutables Event gespeichert. Wer hat wann was getan, ist lückenlos nachvollziehbar — ohne zusätzliche Audit-Infrastruktur.

2. **Keine verlorene Information**: Stornierte, überbezahlte oder korrigierte Posten bleiben im Event-Log erhalten. Es gibt keinen Informationsverlust durch Überschreiben.

3. **Zeitreise möglich**: Der Zustand eines Tisches kann für jeden beliebigen Zeitpunkt in der Vergangenheit rekonstruiert werden, indem die Events nur bis zu diesem Zeitpunkt abgespielt werden. Das ist wertvoll für Fehleranalyse und Reklamationen.

4. **Einfaches Schema**: Eine einzige `events`-Tabelle für alle Operationstypen. Neue Operationstypen (z.B. Umbuchungen, Rabatte) erfordern nur einen neuen Event-Typ — keine Schema-Migration.

5. **Atomare Schreiboperationen**: Ein Event ist ein einzelner `INSERT`, der alle Daten enthält. Keine Transaktionen nötig, keine Gefahr von inkonsistenten Teilschreibungen.

6. **Schema-Evolution ohne Migration**: Neue Event-Typen oder neue Versionen bestehender Typen (`:v2`) können parallel zu alten existieren. Alte Events bleiben unverändert.

7. **Natürliche CQRS-Architektur**: Die Trennung in Commands (Events schreiben) und Queries (Events lesen + Zustand berechnen) ergibt sich organisch aus dem Event-Sourcing-Modell.

#### Nachteile

1. **Höhere Lese-Komplexität**: Jede Abfrage erfordert das Laden und Durchlaufen aller Events eines Tisches (oder ab dem letzten Snapshot). Die Zustandsrekonstruktion ist algorithmisch aufwändiger als ein direkter SQL-Zugriff.

2. **Snapshot-Mechanismus nötig**: Ohne Snapshots wächst die Lesezeit linear mit der Anzahl der Events pro Tisch. Snapshots müssen erstellt, gespeichert und bei der Rekonstruktion berücksichtigt werden — zusätzliche Komplexität.

3. **Keine referenzielle Integrität auf DB-Ebene**: Die `events`-Tabelle hat keine Fremdschlüssel auf `tables` oder `product_variants`. Eine Bestellung auf einen nicht existierenden Tisch würde auf Datenbankebene nicht verhindert. Die Validierung liegt vollständig in der Anwendung.

4. **JSONB-Daten nicht typsicher auf DB-Ebene**: Die `data`-Spalte enthält unstrukturiertes JSONB. Fehlerhafte oder inkompatible Daten können nur durch Anwendungsvalidierung verhindert werden, nicht durch Datenbank-Constraints.

5. **Doppelte Validierung erforderlich**: Sowohl die Event-Daten (`zog`-Schema auf den Event-Data-Struct) als auch die daraus rekonstruierten Domain-Modelle müssen validiert werden, da die Datenbank keine Struktur erzwingt.

6. **Erschwertes Querying für Analysen**: Ad-hoc-Abfragen (z.B. „Umsatz pro Produkt heute") erfordern JSONB-Parsing in SQL oder eigene Projektionslogik in der Anwendung, statt einfacher `GROUP BY`-Abfragen auf typisierten Spalten.

7. **Konzeptuelle Hürde**: Event-Sourcing ist ein weniger verbreitetes Muster als CRUD. Neue Entwickler benötigen mehr Einarbeitungszeit, um die Zustandsrekonstruktion, Snapshots und die Event-Typen-Versionierung zu verstehen.

### CRUD (alternative Implementierung)

#### Vorteile

1. **Direkte Zustandsabfrage**: Balance, offene Posten und Gesamtzahlungen sind per SQL-Aggregation direkt abrufbar, ohne Events in der Anwendung zu durchlaufen. Für einfache Aggregationen wie die Balance ist eine einzelne `SUM`-Query ausreichend.

2. **Referenzielle Integrität**: Foreign Keys auf `tables`, `users` und `product_variants` garantieren auf Datenbankebene, dass keine inkonsistenten Daten gespeichert werden.

3. **Typsichere Spalten**: Alle Felder (Preise, Mengen, IDs) sind als explizite `INT`- oder `TEXT`-Spalten definiert. Die Datenbank erzwingt Datentypen über `CHECK`-Constraints und Spaltentypen.

4. **Einfache Validierung**: Da die Datenbank bereits Typen und Constraints erzwingt, genügt eine einfache Validierung auf Domain-Ebene. Keine doppelte Validierung (Event-Data + Domain-Modell) nötig.

5. **Vertrautes Muster**: CRUD ist das Standardmuster für Webanwendungen. Neue Entwickler können sofort produktiv arbeiten, ohne Event-Sourcing-Konzepte (Zustandsrekonstruktion, Snapshots, Event-Versionierung) lernen zu müssen.

6. **Einfache Ad-hoc-Abfragen**: Umsatzauswertungen, Produktstatistiken und andere Berichte können direkt per SQL mit `GROUP BY`, `JOIN` und Standard-Aggregatfunktionen erstellt werden.

7. **Kein Snapshot-Mechanismus nötig**: Die Leseperformance ist unabhängig von der Anzahl vergangener Operationen, da der Zustand per Aggregation berechnet wird und durch Indizes optimiert ist.

#### Nachteile

1. **Kein natürlicher Audit-Trail**: Der Verlauf ergibt sich nicht automatisch aus der Datenstruktur. Für einen vollständigen Audit-Trail müssten entweder separate Audit-Tabellen, Trigger-basierte Change-Logs oder eine Soft-Delete-Strategie implementiert werden.

2. **Informationsverlust bei Korrekturen**: Wenn Daten direkt aktualisiert werden (z.B. eine falsch erfasste Zahlung korrigieren), geht der ursprüngliche Wert verloren — es sei denn, ein separater Änderungsverlauf wird implementiert.

3. **Komplexere Schreiboperationen**: Jede Bestellung, Zahlung, Lieferung oder Stornierung erfordert eine Datenbank-Transaktion mit mehreren `INSERT`-Statements (Header + Items). Teilweise geschriebene Daten ohne Transaktion würden zu Inkonsistenzen führen.

4. **Schema-Migrationen bei neuen Features**: Neue Operationstypen (z.B. Umbuchungen, Rabatte) erfordern neue Tabellen und Migrationen. Jede Erweiterung des Datenmodells muss durch `ALTER TABLE` oder neue Tabellen abgebildet werden.

5. **Mehr Tabellen und Joins**: 8 Tabellen statt 1 bedeuten mehr Migrationen, mehr Repositories, mehr Testinfrastruktur und komplexere Queries mit mehreren Joins.

6. **Keine Zeitreise**: Der Zustand eines Tisches zu einem vergangenen Zeitpunkt kann nur dann rekonstruiert werden, wenn zusätzlich Timestamps und ggf. Versionierung auf den Daten gepflegt werden. Dies ist aufwändig und fehleranfällig.

7. **Komplexe SQL für Positions-Aggregation**: Die Abfrage unbezahlter oder ungelieferter Positionen erfordert verschachtelte Subqueries über mehrere Tabellen (siehe Beispiel oben). Diese Queries sind schwerer lesbar und wartbar als der äquivalente Go-Code im Event-Sourcing-Ansatz.

8. **Fehlende Immutabilitätsgarantie**: Ohne explizite Maßnahmen (DB-Trigger, Read-Only-Views) können Operationsdaten nachträglich verändert werden. Im Event-Sourcing ist die Immutabilität durch die Append-Only-Architektur strukturell erzwungen.

---

## Zusammenfassung und Empfehlung

### Zusammenfassung

Beide Ansätze lösen dasselbe Problem — die Persistierung und Abfrage von Tisch-Operationen —, aber mit fundamental unterschiedlichen Kompromissen:

**Event-Sourcing** speichert nicht den aktuellen Zustand, sondern die Geschichte aller Zustandsänderungen. Das garantiert einen lückenlosen Audit-Trail, ermöglicht Zeitreisen und macht das Schema flexibel erweiterbar. Der Preis ist eine höhere Lese-Komplexität (Zustandsrekonstruktion + Snapshots), fehlende referenzielle Integrität auf DB-Ebene und eine steilere Lernkurve.

**CRUD** speichert die operativen Daten direkt in typisierten, relationalen Tabellen. Das ermöglicht direkte SQL-Abfragen, referenzielle Integrität und einfache Ad-hoc-Analysen. Der Preis ist ein höherer Migrationsaufwand bei neuen Features, das Fehlen eines natürlichen Audit-Trails und komplexere Schreiboperationen mit Transaktionen.

| Kriterium                     | Event-Sourcing      | CRUD               |
| ----------------------------- | ------------------- | -------------------|
| Audit-Trail                   | ✅ Strukturell gegeben | ⚠️ Zusätzlicher Aufwand nötig |
| Zeitreise                     | ✅ Möglich           | ❌ Nicht ohne Weiteres |
| Schema-Flexibilität           | ✅ Neue Event-Typen  | ⚠️ Schema-Migrationen |
| Referenzielle Integrität      | ❌ Nur in Anwendung  | ✅ Durch DB erzwungen |
| Typsicherheit auf DB-Ebene    | ❌ JSONB             | ✅ Explizite Spalten |
| Leseperformance (einfach)     | ⚠️ Rekonstruktion    | ✅ Direkte Abfrage |
| Leseperformance (komplex)     | ⚠️ Snapshots nötig   | ⚠️ Komplexe Joins |
| Schreibperformance            | ✅ Single-Insert     | ⚠️ Transaktion mit N+1 Inserts |
| Ad-hoc-Analysen               | ⚠️ JSONB-Parsing     | ✅ Standard-SQL |
| Einstiegshürde                | ⚠️ Höher             | ✅ Niedriger |
| Tabellenanzahl (Operationen)  | ✅ 1                 | ❌ 8 |
| Immutabilität                 | ✅ Strukturell       | ⚠️ Muss extra umgesetzt werden |

### Empfehlung

Für jotti ist **Event-Sourcing der geeignetere Ansatz**, aus folgenden Gründen:

1. **Audit-Trail ist eine Kernanforderung.** In einem Kassensystem muss nachvollziehbar sein, wer wann was bestellt, bezahlt, geliefert oder storniert hat. Event-Sourcing liefert das automatisch, ohne zusätzliche Audit-Infrastruktur. Eine CRUD-Implementierung müsste diese Funktionalität separat aufbauen und pflegen, was die vermeintliche Einfachheit des CRUD-Ansatzes relativiert.

2. **Immutabilität schützt vor Manipulation.** In einem System, das Geldbeträge verwaltet, ist es wichtig, dass einmal erfasste Operationen nicht nachträglich verändert werden können. Event-Sourcing erzwingt das strukturell (Append-Only-Store mit DB-Triggern). In einem CRUD-System müsste diese Garantie separat implementiert werden.

3. **Die Komplexitätskosten von Event-Sourcing sind in jotti begrenzt.** Die Zustandsrekonstruktion betrifft nur Tisch-Operationen, nicht das gesamte System. Stammdaten werden weiterhin per CRUD verwaltet. Die hybride Architektur hält die Event-Sourcing-Komplexität auf einen überschaubaren Bereich begrenzt.

4. **Snapshots adressieren das Performance-Problem.** Die lineare Lese-Komplexität, der größte praktische Nachteil von Event-Sourcing, wird durch den Snapshot-Mechanismus effektiv abgemildert. In der Praxis werden Tische regelmäßig abgerechnet — die Event-Kette pro Tisch bleibt kurz.

5. **Schema-Flexibilität zahlt sich aus.** Zukünftige Features wie Umbuchungen zwischen Tischen, Rabattaktionen oder Trinkgeld-Erfassung erfordern nur neue Event-Typen, keine Schema-Migrationen. Das reduziert das Risiko von Datenmigrations-Fehlern im Produktivbetrieb.

Der CRUD-Ansatz wäre eine valide Alternative, wenn der Audit-Trail keine Rolle spielen würde oder wenn häufige, komplexe Ad-hoc-Abfragen auf den Operationsdaten notwendig wären. Für den konkreten Anwendungsfall von jotti — ein Kassensystem mit Nachvollziehbarkeitsanforderungen — überwiegen die Vorteile des Event-Sourcing-Ansatzes.
